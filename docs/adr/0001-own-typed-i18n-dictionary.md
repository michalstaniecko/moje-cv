# Own typed translation dictionary instead of i18next

The Interface language needs ~250 strings, used by both the main process (menu, native dialogs) and the renderer. It started with two languages (en, pl) and now has sixteen (en, pl, es, fr, de, pt, it, nl, ru, uk, tr, id, vi, cs, ro, sv). We use our own dictionary module shared by both processes: `en` is the source of truth and every other language must satisfy its type, so a missing translation is a compile error in every language at once; plurals go through `Intl.PluralRules` (which already knows the categories of all sixteen) and parametrised strings are plain functions. All dictionaries are bundled and loaded eagerly: sixteen small modules cost far less than a loader. We rejected i18next + react-i18next because it adds dependencies, needs extra setup to get typed keys, and its runtime features (lazy loading, namespaces, ICU parsing) solve problems a desktop app with bundled dictionaries doesn't have. The sixteen languages were translated by an agent and are reviewed by native speakers separately; the dictionaries stay TypeScript files edited by developers. Revisit if translations ever move to non-developers or a translation platform, which would need a file format such as JSON or XLIFF.
